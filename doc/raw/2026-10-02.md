## Case 1: 모의투자 불가 판명 — 실전 키 읽기 전용 + paper/memory 시뮬레이션으로 방향 전환

### Grounding
- Git Context: `hash:5dc624b`
- Evidence: 칸반(done 79 기준), kis-api 위키 pending 항목, 오너 판정 전달(대화)
- Confidence: 5/5 (방향 결정 자체; 배경 사유는 오너 진술)

### Design Decision
오너가 한국 복귀 후 한국투자증권 모의투자 서비스 신청을 시도했으나 **불가능**함을 확인.
오너 원문: "시팔 한국투자증권 글렀다 모의투자 불가능이야. 현재 상태로 진행해야할듯"

결정: paper+kis+mock 도메인 실증 경로를 폐기목록으로 옮기지는 않되(스펙 지식은 유효),
**당분간 갈 수 없는 길로 명시**하고 다음 경로로 진행한다.

1. **실전 키 읽기 경로 완성**: 잔고(TTTC8434R)·당일체결(TTTC0081R, 커뮤니티 문서
   기반 필드)·WS approval key/H0STCNT0 실시간 체결가 — 전부 조회 전용이라 실전
   도메인에서 안전(주문 불가). 백필(FHKST03010100)·tokenP는 09-20 실증 완료.
2. **시뮬레이션 = 실데이터 + MockBroker**: 모의 도메인 없이 TRADING_MODE=paper +
   PAPER_BACKEND=memory + 실시간 실시세/실봉으로 paper 가동. 체결 모델은 MockBroker
   (즉시·부분체결 없음) — 한계를 인지하고 사용.
3. **주문 경로(실전)는 계속 봉인**: paper+kis+real 이중 가드(09-20 Case 5) 유지.
   live 진입은 별도 판단(이중 확인 + 최소 수량 실증 설계 필요 시점에 재의).

### Alternatives Considered
- Option A: 타 증권사 모의(키움 등)로 주문 경로 실증 — 기각: KIS 클라이언트 전체가
  KIS 스펙으로 작성됐고, 증권사를 바꾸는 건 재작성이지 실증이 아님.
- Option B: live 최소 주문(1주)으로 주문 경로 직접 실증 — 보류: 읽기 경로·시뮬레이션
  검증 없이 첫 실주문이 첫 REST 실증이 되는 건 리스크 배치 반대. 필요 시점에 재의.
- Selected: 읽기 전용 실증 + 실데이터 시뮬레이션 (위 결정 1·2·3).

### Analysis
- Context: 실전 키만 보유 상태(09-20 Case 5)에서 "모의 키 확보 후 주문 실증"이
  유일한 남은 KIS 갭이었는데, 모의 신청 자체가 막혀 계획을 재편해야 함.
- **Trade-offs**: 시뮬레이션 체결 품질(슬리피지·부분체결 없음) vs 검증 가능성 —
  실데이터 진입/청산 판단은 검증하되 체결 미세구조는 라이브 전 별도 과제로 남음.
- Reversibility: High (모의 키가 언제든 확보되면 기존 카드 경로로 복귀 가능)

- **Anti-Patterns**: 모의 도메인 없음을 이유로 live를 서두르기 — 읽기 경로 실증이

## Case 2: 실시간 시세 런타임 배선 — 실전송 구현체와 "당일 틱은 히스토리에 없다" 테스트 설계

### Grounding
- Git Context: `hash:5dc624b`(작업 시작 시점)
- Evidence: `config.rs`(QuotesSource), `kis/ws.rs`(TungsteniteConnection/Factory), `runtime/realtime.rs`, `main.rs`, `scripts/dev/run-realtime.ps1`, 칸반 done 카드
- Confidence: 5/5

### Discovery
카드 "실시간 시세 런타임 배선" 구현 중 두 가지 비자명 사실:

1. **실전송 구현체가 없었다.** `kis/ws.rs`의 ConnectionFactory는 테스트 가짜만 있었고
   "real implementation wraps tokio-tungstenite"는 주석만 존재. tungstenite 의존성
   추가(plain ws — KIS 실시간 엔드포인트는 `ws://`라 TLS 불필요)와 함께
   TungsteniteConnection 구현. `WsConnection::pong()`이 **동기** 시그니처라 응답
   전송에 `tokio::spawn` 파이어앤포겟이 필요했다(트레이트 변경 대신).
2. **당일 틱은 집계기에서 봉 확정 전까지 히스토리에 들어가지 않는다**(look-ahead
   원천 차단, 설계된 동작). 첫 테스트가 "라이브 틱 가격이 골든크로스를 만든다"를
   전제로 실패 — 스트래티지가 보는 건 백필 시드 봉뿐이고, 크로스도 **마지막 완결
   봉에서의 전환 이벤트**(상태 아님)여야 신호가 나온다.

### Fix Code
- 시드: 평평(1000×20) → 딥(960×5) → 완만회복(970×4) → 돌파(1200) — 마지막 봉에서
  fast(5)=1016 > slow(20)=994 전환 발생. 틱은 의사결정 사이클 트리거로만 기여.
- 로컬 WS 서버(tokio-tungstenite accept_async)를 띄우는 e2e 테스트로 실전송 검증:
  구독 메시지(approval_key 포함) 수신 → 시세 프레임 → Quote 콜백 → PINGPONG 에코.
- QUOTES_SOURCE=kis 무자격 기동: settings 로드 단계에서 거부(실동작 확인).

### Analysis
- Why non-obvious: 배선 카드의 진짜 공백은 "WS 클라이언트 연결"이 아니라 ①전송
  계층 부재 ②히스토리 시딩(seed_daily_close — SimLoop는 전량 재생으로 해결하던
  문제를 실시간은 시딩으로) ③동기 콜백→mpsc 채널 역결합이었다.
- Verification: **164 passed**(+5), clippy 0, fmt 클린.
- 시세 버스트 방지: 의사결정+영속화 500ms 스로틀, 종목별 최신 틱만 저장.

### Related Knowledge
- Concepts: [[kis-api]], [[trading-core-determinism]]
- **Anti-Patterns**: (1) "실시간 틱이 지표를 움직인다" 전제의 테스트 — 당일 틱은
  봉 확정 전까지 지표에 안 들어간다. (2) 동기 트레이트에 await 끼워넣기 — 파이어앤
  포겟 스폰으로 경계를 유지할 것

### Design Decision
오너 원문: "내컴퓨터에서 돌리자고했자나. 서버는 꼭 피닉스에서 떠야하나?"

  변경 추가.
- Option B: 로컬 우선 + 피닉스 카드 주차(선택) — 채택. 운용 관건은 장중 절전 금지.

## Case 5: 백필 500 3종목 전멸 — KIS 공식 "1일 1회 발급 원칙" 공지와 90초 자동 재시도

### Grounding
- Git Context: `hash:5dc624b` + main.rs 재시도 패치
- Evidence: 오너 실행 로그(원문 아래), KIS 공식 발급 안내 SMS/메일(오너 전달)
- Confidence: 5/5

### Error (실전, 원문)
```text
backfill: 3 symbols x 5y -> D:\Project\LossFunction\data\lossfunction.db (domain: real)
  005930: FAILED — source failure: Server: server error 500
  035420: FAILED — source failure: Server: server error 500
  069500: FAILED — source failure: Server: server error 500

```
KIS 공지 원문(발급 정상 확인됨): "접근 토큰은 1일 1회 발급 원칙이며, 유효기간내

### Analysis
- 진단: 오류 출처는 rest.rs 차트 요청(FHKST03010100)의 서버 500 — tokenP 발급
  자체는 성공(공지 = 그 발급 알림). 09-20 Case 9와 동일 패턴(단기 제한은

  재실행하면 제한이 깊어진다.
- Fix: main.rs 백필 CLI에 **서버 500 재시도 1회(90초 대기) 추가** — 프로세스 내
  KisAuth 토큰 캐시를 재사용하므로 재발급 없이 재시도. 라이브러리/주문 경로는
  원칙(fail-loud, 5xx 정책은 위키) 그대로.
- 시세 시뮬레이션(run-realtime)은 tokenP를 쓰지 않는다(approval key 별도 엔드포인트)
  — 백필 실패와 무관하게 가동 가능.

### Related Knowledge

- **Anti-Patterns**: KIS 500/403에 즉시 재실행 폭주 — 90초 대기 없이 프로세스를

## Case 6: H0STCNT0 실측 47열 — 공식 문서 46열과 실데이터의 간극, 첫 실틱 실증

### Grounding
- Git Context: `hash:5dc624b` + ws.rs 47열 패치
- Evidence: 오너 콘솔 로그(원문 아래), ws_tests.rs parses_measured_production_frame
- Confidence: 5/5

### Error (실전, 원문 — 최초 관측)
```text
ws system message: {"header":{"tr_id":"H0STCNT0","tr_key":"005930","encrypt":"N"},"body":{"rt_cd":"0","msg_cd":"OPSP0000","msg1":"SUBSCRIBE SUCCESS","output":{"iv":"82c7bcb429d16bd6","key":"ubzhvfmtscsnydpkqdxaamrwematutho"}}}
ws frame parse failed: frame field count 47 not a multiple of 46 — head: 0|H0STCNT0|001|069500^144508^111830^...
ws frame parse failed: frame field count 141 not a multiple of 46 — head: 0|H0STCNT0|003|005930^144508^275250^...
first live tick: 069500 @ 111725
first live tick: 005930 @ 275000
first live tick: 035420 @ 192000
```

### Discovery
1. **실측 프레임은 레코드당 47열** — 공식 문서/샘플 기반 46열 테이블이 실데이터의
   모든 틱을 파싱 실패로 버렸다(141=3×47 정확히 정렬). 전체 프레임 덤프로 열
   위치 검증: [33]BSOP_DATE=20261002, [35]TRHT_YN=N, [45]VI_STND_PRC 등 0~45열은
   기존 테이블 그대로 정확 — 마지막 [46]에 미문서화 열(값 '2')이 존재.
2. **3번째 파이프 필드는 건수**("001"|"003")다 — tr_key가 아님. 한 프레임에
   같은 초의 체결 다발이 멀티레코드로 온다.
3. **구독 ACK 형상**: rt_cd 0 / OPSP0000 / SUBSCRIBE SUCCESS + output에 iv·key
   (AES 소재로 추정 — 체결통보 암호화용). 거부 시 이 메시지로 사유가 온다.
4. PINGPONG은 JSON으로 오고 조용히 처리됨 — 연결이 수 분+ 살아있고 틱이 계속
   흐르는 것이 keepalive 응답 동작의 실증.

### Fix Code
- H0STCNT0_COLUMNS 47열화(UNDOCUMENTED_FIELD_47 명시 + 의미 미확정 주석).
- 관측: 구독 ACK/시스템 메시지 전부 콘솔 노출, 파싱 실패 첫 프레임만 전체 덤프,
  종목당 첫 틱 로그(first live tick).
- 실측 프로덕션 프레임(3레코드, 005930@274750)을 회귀 테스트로 고정.

### Analysis
- Why non-obvious: "공식 샘플로 검증했다"는 스펙이 실데이터에선 부족했다 —
  열 개수 자체가 문서와 달랐고, 침묵하는 파서가 원인을 숨겼다. 관측 로그를
  먼저 깔고 한 사이클 만에 원인 확정(16자 헤드만으론 불가, 전체 덤프가 결정적).
- Verification: WS 테스트 11/11(실측 프레임 회귀 포함), 장중 실틱 3종목 실증,
  스파크라인 25초 간 변화로 연속 유입 확인.
- 칸반 "KIS 실시간 체결가 WS 실증" 당일 완결(계획보다 3일 앞섬).

### Related Knowledge
- Concepts: [[kis-api]], [[fail-loud]]
- **Anti-Patterns**: (1) 파싱 실패/시스템 메시지의 침묵적 드롭 — 실측 디버깅의
  첫 원수 (2) 문서 기반 열 테이블을 실측 없이 신뢰하기 — 실측 프레임 회귀
