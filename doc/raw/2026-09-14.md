## Case 1: Python 패키지 스캐폴드 설계 결정 (src layout + hatchling + optional-dependencies)

### Grounding

- Evidence: pyproject.toml, src/lossfunction/, tests/test_scaffold.py
- Confidence: 4/5

### Design Decision
LossFunction Python 패키지 기반을 다음과 같이 확정했다:
- **src layout** (`src/lossfunction/`) — cwd import 오염 방지, 테스트가 설치된 패키지를 검증
- **hatchling** build backend — 설정 최소, PEP 621 준수
- **dev 의존성은 `[project.optional-dependencies].dev`** — `pip install -e ".[dev]"`로 설치
- **ruff**로 lint+format 통합 (line-length 100, select: E/W/F/I/UP/B/SIM)
- **pytest** (testpaths=["tests"], addopts="-q")
- Python 하한 `>=3.11` (개발환경 3.13.5, OCI 배포 호환 고려)

### Alternatives Considered
- Option A: flat layout (`lossfunction/` 최상위) — cwd에서 미설치 상태로 import되어 테스트가 설치 상태를 검증 못 함. 기각.
- Option B: PEP 735 `[dependency-groups]` — 구형 pip에서 미지원, OCI 포함 환경 호환 리스크. 기각.
- Option C: setuptools — 동작하지만 pyproject 설정 장황. 기각.
- Selected: src layout + hatchling + optional-dependencies — 호환성과 검증 품질의 균형.

### Decision Code
```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "lossfunction"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6"]
```

## Case 3: Broker 인터페이스 설계 — async ABC + idempotency key + frozen records

### Grounding
- Git Context: `hash:12dba89`
- Evidence: src/lossfunction/broker/base.py, src/lossfunction/broker/mock.py, tests/test_broker.py
- Confidence: 4/5

### Design Decision
- `Broker`는 **async ABC**: submit_order, cancel_order, get_execution_report,
  get_positions, get_quote. WS 기반 런타임(event loop)과의 정합성 때문에 동기보다
  async로 확정. blocking 구현은 스레드로 오프로드하는 것이 구현 책임.
- `OrderRequest.client_order_id`를 **idempotency key**로 규격화: 동일 id 재제출은
  같은 주문으로 간주(중복 주문 방지의 첫 관문).
- `ExecutionReport`에 `open` 필드와 누적 체결 필드를 두어 restart reconciliation이
  broker 보고를 source of truth로 쓸 수 있게 함.
- 모든 record는 pydantic `frozen=True` — 생성 후 불변.
- 가격 `Decimal`, 수량 `int`(국내 주식 소수 주문 불가), 심볼 `^\d{6}$` 패턴.
- `get_execution_report`는 timeout 후 UNKNOWN 해소의 표준 조회 경로.

### Alternatives Considered
- Option A: 동기 인터페이스 — REST에는 단순하지만 WS 런타임에서 스레드 관리 부담,
  전체 시스템이 async로 감. 기각.
- Option B: 시세 구독(subscribe)까지 Broker에 포함 — marketdata 모듈로 분리하기로
  함(아키텍처 문서). 이 카드 범위 밖, KIS WS 카드에서 확정.
- Selected: async ABC 최소 집합(주문/조회) — mock/live/backtest가 같은 경계를 공유.

### Discovery
- `lossfunction.broker.__init__`에서 `MockBroker` export 누락 시 테스트 수집 단계에서
  `ImportError: cannot import name 'MockBroker'` — 새 모듈 추가 시 `__init__` export
  목록 갱신 필수.

### Verification
- `pytest` → `23 passed` (abstract 인스턴스화 금지, mock 준수, idempotency,
  average-price blending, cancel/open, sell 방어, frozen 검증 포함)
- `ruff check`/`format` → 통과

## Case 4: KIS 인증 스펙 확인 및 토큰 클라이언트 구현

### Grounding
- Git Context: `hash:4228a47`
- Evidence: src/lossfunction/broker/kis/auth.py, tests/test_kis_auth.py, 공식 샘플
  koreainvestment/open-trading-api examples_llm/kis_auth.py
- Confidence: 4/5

### Discovery
KIS 접근토큰 발급의 실제 스펙 (공식 샘플 코드로 검증):
- Endpoint: `POST {base}/oauth2/tokenP` — **JSON body**
  `{"grant_type": "client_credentials", "appkey": ..., "appsecret": ...}`
  (form-urlencoded `/oauth2/token` 도 존재하나 공식 샘플은 tokenP 사용)
- 200 응답: `access_token`, `access_token_token_expired`
  (`"%Y-%m-%d %H:%M:%S"` 형식, **KST 월시간, 타임존 마커 없음** → 파싱 시
  `timezone(timedelta(hours=9))` 부여 필수)
- 토큰 유효기간 약 1일. 6시간 이내 재발급 요청은 서버가 동일 토큰 반환.
- 도메인: 실전 `https://openapi.koreainvestment.com:9443`,
  모의 `https://openapivts.koreainvestment.com:9443`
- WebSocket 접속키는 별도 endpoint `POST /oauth2/Approval`
  (body 필드명이 `appsecret`이 아니라 **`secretkey`**) — WS 카드에서 구현.

### Design Decision
- 토큰 캐시 + 만료 5분 전 proactive 재발급 (refresh margin).
- double-checked lock으로 동시 호출 single-flight (발급 요청 1회로 병합).
- 에러 분류 `AuthErrorKind`: invalid_credentials(401/403, 재시도 금지),
  rate_limited(429, 재시도), server_error(5xx, 재시도), network(전송 실패,
  재시도), malformed_response(200이지만 파싱 불가, 재시도 금지).
- 백오프: 0.25s * 2^(attempt-1), 최대 3회 재시도. clock/sleep 주입 가능.
- Settings에 `kis_environment`(기본 mock) 추가, live 모드는 real 강제.

### Error (테스트 작성 실수)
```
AssertionError: assert 1 == 2
```
원인: "만료 10분 전 → 마진 지나 재발급"이라 쓴 테스트 전제가 반전됨.
만료 10분 전은 5분 마진 기준 **아직 유효**(유효 잔여 > 마진)이므로 캐시 유지가
정상 동작. 재발급은 만료 4분 전(마진 이내)에 발생. 테스트를 마진 경계 양쪽으로
수정. 구현 코드는 무결 — `now < expires_at - margin`이 유효 판정.

### Verification
- `pytest` → `35 passed` (발급/캐시/마진/만료/재시도 정책/싱글플라이트/도메인 매핑)
- `ruff check`/`format` → 통과

### Related Knowledge
- Concepts: [[kis-api]], [[kis-tokenp]], [[kst-timezone]]
- Patterns: [[single-flight-token]], [[retryable-error-classification]]
- **Anti-Patterns**: refresh margin 방향 혼동 (만료 전 margin **이내**가 재발급 시점)

## Case 5: KIS REST endpoint 스펙과 에러 분류 설계

### Grounding

### Discovery
국내주식 핵심 3 endpoint의 실제 스펙 (공식 샘플 코드로 검증):
- **주문** `POST /uapi/domestic-stock/v1/trading/order-cash`
  tr_id: 실전 매수 TTTC0012U / 매도 TTTC0011U, 모의 V prefix(VTTC0012U/VTTC0011U).
  body는 **대문자 키 + 전부 문자열**(CANO, ACNT_PRDT_CD, PDNO, ORD_DVSN,
  ORD_QTY, ORD_UNPR, EXCG_ID_DVSN_CD...). ORD_DVSN: 00=지정가, 01=시장가.
  시장가 주문은 ORD_UNPR="0". 응답 output.ODNO가 주문번호.
- **잔고** `GET /uapi/domestic-stock/v1/trading/inquire-balance`
  tr_id: 실전 TTTC8434R / 모의 VTTC8434R. 페이지네이션은 **응답 헤더
  tr_cont가 M/F인 한** body의 ctx_area_fk100/ctx_area_nk100을 다음 요청에
  CTX_AREA_FK100/NK100으로 반송하며 연속 조회. 보유수량 0 행 존재 가능.
- **시세** `GET /uapi/domestic-stock/v1/quotations/inquire-price`
  tr_id FHKST01010100(실전=모의 동일). 파라미터 FID_COND_MRKT_DIV_CODE=J(KRX),
  FID_INPUT_ISCD=종목코드. 현재가 필드는 `stck_prpr`.

### Design Decision
- 에러 분류 `APIErrorKind`: network(전송 실패, 재시도), server_error(5xx, 재시도),
  rate_limited(429, 재시도), invalid_token(401/403), api_reject(**HTTP 200인데
  rt_cd != 0**, 비즈니스 거부 — 재시도 금지), malformed_response.
- **401은 한 번만 토큰 재발급 후 재시도**: auth.invalidate() → 새 토큰 → 같은
  요청 재송. 두 번째 401이면 실패. 토큰 만료가 주문 실패로 번지지 않게.
- audit trace: HTTP 시도마다 AuditRecord(request_id, attempt, tr_id, path,
  http_status, rt_cd, msg_cd, elapsed_ms, timestamp, environment,
  order_summary). **헤더/자격증명은 절대 포함하지 않는다** — 테스트가
  appsecret/token 누출 부재를 검증.
- KISRestClient는 아직 Broker ABC 구현이 아님(주문/잔고/시세 래퍼).
  cancel/체결조회 endpoint는 reconciliation 카드에서 추가, Broker 조립은
  paper/live 분리 카드에서 완성.

### Error (분류 순서 결함)
```
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```
503 + 비-JSON body(text) 응답에서 JSON 파싱을 상태 코드 체크 **전에** 실행해
MALFORMED로 오분류되고 재시도 없이 즉시 실패. 수정: 상태 코드 선분류 → 200일
때만 JSON 파싱. "파싱은 성공 응답에만" 원칙.

- `ruff check`/`format` → 통과

## Case 6: KIS WebSocket 스펙과 재구독(replay) 설계 + 교착 디버그

### Grounding
- Git Context: `hash:ff1e528`
- Evidence: src/lossfunction/marketdata/kis_ws.py, tests/test_kis_ws.py, 공식 샘플
  kis_auth.py(KISWebSocket/data_fetch/auth_ws), domestic_stock_functions_ws.py
- Confidence: 4/5

### Discovery
KIS WebSocket 실제 스펙 (공식 샘플 코드로 검증):
- **WS URL**: 실전 `ws://ops.koreainvestment.com:21000`, 모의
  `ws://vops.koreainvestment.com:21000` (config 키 ops/vops)
- **접속키**: `POST {rest_base}/oauth2/Approval`, JSON body
  `{"grant_type": "client_credentials", "appkey", "secretkey"}` — 필드명이
  **`secretkey`** (REST 토큰의 `appsecret`과 다름!). 응답 `approval_key`.
- **구독 메시지**: `{"header": {"approval_key", "tr_type": "1"|"0",
  "custtype": "P"}, "body": {"input": {"tr_id", "tr_key"}}}`
- **데이터 프레임**: 파이프 구분 `0|TR_ID|TR_KEY|값1^값2^...` — 4번째 필드가
  `^` 구분 레코드. H0STCNT0(실시간체결가 KRX) 컬럼은 **46개**(공식 순서).
  주요 인덱스: MKSC_SHRN_ISCD=0, STCK_CNTG_HOUR=1, STCK_PRPR=2, BSOP_DATE=33.
- **PINGPONG**: 서버가 JSON 메시지(header.tr_id=="PINGPONG")로 keepalive →
  클라이언트가 pong으로 echo.
- **체결통보**(주문 알림): 실전 H0STCNI0, **모의 H0STCNI9**, AES256 암호화 —
  reconciliation 카드에서 다룰 예정.

### Design Decision
- **desired subscription을 클라이언트 객체의 도메인 상태로 유지**, 재연결 시
  전량 replay. connection-local 상태로 관리하면 재연결 후 시세가 끊긴다는
  실패 사례를 구조적으로 원천 차단.
- 재연결 백오프 1→2→4→...→30초 상한. 연결 실패도 같은 루프에서 재시도.
- **프레임 파싱 실패(ValueError)는 연결 끊김이 아니다** — 해당 프레임만
  버리고 연결 유지. recv 실패만 disconnect로 분류.
- 연결 계층 주입(ConnectionFactory)으로 네트워크 없이 재연결/재구독/파싱
  전 경로 테스트. 실제 구현은 websockets 라이브러리 얇은 어댑터.

### Error (컬럼 수 불일치 → 무한루프 교착)
```
ValueError: frame field count 48 not a multiple of 46
```
테스트 헬퍼가 H0STCNT0 프레임을 48칸으로 생성(실제 46). 이때 파싱 실패가
disconnect로 분류되어 재연결 → 재실패 → 재연결... 주입된 sleep이 즉시
반환되며 이벤트 루프에 제어를 양보하지 않아 테스트가 영구 교착.
**교훈 2가지**: (1) 프레임 길이는 상수(H0STCNT0_COLUMNS)에서 파생시킬 것,
매직 넘버 금지. (2) 주입 sleep noop는 `await asyncio.sleep(0)`이라도 양보
하게 만들 것 — 실패 경로의 무한 루프가 루프 전체를 얼린다.

### Verification
- `pytest` → `54 passed` (파싱 단일/복수/거부, 구독 메시지 형상, 재연결+
  replay 후 시세 재개, PINGPONG echo, unsubscribe 미재생, approval key body)
- `ruff check`/`format` → 통과

### Related Knowledge
- Concepts: [[kis-api]], [[kis-websocket]], [[desired-state-replay]]
- Patterns: [[injectable-connection-factory]], [[parse-vs-disconnect-separation]]
- **Anti-Patterns**: subscription을 connection 상태로 관리(재연결 시 유실);
  매직 넘버 컬럼 인덱스; 양보 없는 noop sleep

  받으므로 미래 데이터 접근 경로 자체가 없음. 스파이 전략으로 "모든 결정
  시점의 견적 시각 ≤ 해당 바 시각"을 구조적으로 검증.
- 비용: 커미션(양방향) + 증권거래세(매도만), Decimal 정확 계산. 현금 흐름은
  매수 −(노셔널+수수료), 매도 +(노셔널−수수료−세금). 바별 equity 곡선.
- **전략 재사용**: 백테스트가 라이브와 동일한 사건 형상(스냅샷→결정→리스크→
  체결)을 사용 — MockBroker 크로스 체결 덕분에 동일 Strategy 클래스가 양쪽
  에서 실행됨. 백테스트 전용 전략 API를 만들지 않는다.
- 미체결 지정가는 비용 0 (체결 없음 = 수수료 없음 테스트).

  동등, 미체결 비용 0, 미래 바 접근 거부/미정렬 거부/스파이 스냅샷,
