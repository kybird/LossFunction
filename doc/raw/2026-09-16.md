## Case 1: VSCode 터미널이 존재하지도 않는 .pgenv를 conda 활성화 — Python 청산 후 유령 환경

### Grounding
- Git Context: `hash:4958e4f`
- Evidence: `%APPDATA%\Code\User\workspaceStorage\4fc6d7958ab5bdd0016cb92c8ed4c511\state.vscdb`, `.pgenv/conda-meta/history`(삭제 전), `.pgdata16/postmaster.pid`(삭제 전)
- Confidence: 5/5

### Error
```text
rm: cannot remove '.pgenv/Library/bin': Device or resource busy
```
사용자 목격 증상: VSCode에서 Ctrl+` 로 터미널을 열 때마다 Rust 프로젝트인데도 `(.pgenv)` conda 활성화가 주입됨.

VSCode 내부 DB에 저장되어 있던 자동 선택 기록(원문):
```json
"autoSelectedWorkspacePythonInterpreter-d:\\Project\\LossFunction":
  {"id":"D:\\Project\\LossFunction\\.pgenv\\python.exe","sysPrefix":"D:\\Project\\LossFunction\\.pgenv",
   "envType":"Conda","envPath":"D:\\Project\\LossFunction\\.pgenv",
   "path":"D:\\Project\\LossFunction\\.pgenv\\python.exe","version":{"raw":"","major":-1,...}}
```
`.pgenv` 생성 기록(`conda-meta/history` 원문):
```text
# cmd: C:\Users\admin\miniconda3\Scripts\conda-script.py create -y -p D:\Project\LossFunction\.pgenv -c conda-forge postgresql
```

### Environment Context
- Windows 11, VSCode(Python 확장, `python.condaPath` = miniconda3), Git Bash
- `.pgenv`는 conda-forge postgresql 18 환경 — **python.exe가 없는 순수 PG 바이너리 환경**
- Migration Issue: No — Rust 마이그레이션 완료 후 잔존물 청산 실패 사례

### Discovery
- VSCode Python 확장은 conda 환경을 `python.exe`가 아니라 폴더의 `conda-meta/history` 유무로 식별한다. 그래서 파이썬이 전혀 없는 `.pgenv`조차 "Conda 환경"으로 발견해 워크스페이스 기본 인터프리터로 **자동 선택**했다(가리키는 `.pgenv\python.exe`는 존재한 적 없고 version.major=-1).
- 이 자동 선택 기록은 저장소가 아니라 `AppData\...\workspaceStorage\<hash>\state.vscdb`(SQLite)에 저장된다. 코드를 아무리 정리해도(git status clean) 이 기록은 프로젝트 상태와 무관하게 살아남아, `python.terminal.activateEnvironment`(기본 true)이 매 터미널마다 `conda activate .pgenv`를 주입했다.
- gitignore된 무거운 산물(.pgenv 167M + .pgenv16 313M + .venv 311M + .pgdata 65M + .pgdata16 47M ≈ 900MB)은 git이 안 보이므로 "마이그레이션 완료" 상태에서도 디스크에 그대로 남는다.
- `.pgenv16`의 PG 서버(postmaster PID 9460)가 **2일째 계속 실행 중**이었고, `.pgenv\Library\bin\ccapiserver.exe`(PID 46848, 부모 사망·TCP 없음·저장소 무언급)라는 고아 프로세스가 디렉터리를 잡고 있어 삭제가 막혔다.

### Analysis
- Why non-obvious: 활성화의 원인이 프로젝트 파일(추적/무시 여부 무관)이 아니라 VSCode의 내부 DB에 있어서, 저장소를 아무리 뒤져도 원인이 안 나온다. 게다가 선택된 "인터프리터"는 실존한 적 없는 경로.
- Action taken:
  1. `pg_ctl -D .pgdata16 stop -m fast`(Case 7의 최소 PATH 격리)로 PG 정상 종료 — 크래시 없이 깨끗하게 내려감.
  2. 좀비 `conda.exe`(전일 시작)와 고아 `ccapiserver.exe` 종료 후 `.pgenv .pgenv16 .pgdata .pgdata16 .venv .pytest_cache .ruff_cache` 전부 삭제.
  3. `.vscode/settings.json`(gitignore됨)에 `"python.terminal.activateEnvironment": false` — VSCode 실행 중에는 state.vscdb 수정이 되살아나므로, 파일 기반 설정으로 터미널 주입을 확정 차단. 근원 기록은 명령 팔레트 "Python: Clear Workspace Interpreter Settings"로 지울 수 있음.
- Verification: `git status` clean(기존 미추적 `doc/kanban/board.html`만 존재), `cargo test` → **108 passed; 0 failed**.

### Related Knowledge
- Concepts: [[storage-sqlite]](PG 청산의 원래 이유), [[vscode-python-env-autoselection]]
- **Anti-Patterns**: 마이그레이션 완료 판정을 git 추적 파일만으로 내리기 — gitignore된 런타임 산물(환경·데이터·서버 프로세스)은 별도 체크리스트 없으면 영원히 남는다

### Grounding
- Git Context: `hash:4958e4f`
- Evidence: `git log --follow -- docs/architecture.md`(작성 e4aa2d8 → 마지막 수정 46f3713 SQLite 전환), `rust/lossfunction/src/lib.rs`
- Confidence: 5/5

### Error
소유자가 코드 독학 시작하며 발견. 문서에 남아 있던 Python 시절 서술(원문):

§4 모듈 표 → 실제 모듈(types/history/domain/strategy+risk/execution/kis/broker/storage/runtime/backtest/analysis/config/reference).

**회귀(커밋 6bb28d5 후 발견)**: 수정한 라벨에 따옴표 없는 괄호를 넣어 Mermaid 파서가 다이어그램 전체를
렌더하지 못함(원문):

## Case 3: 시크릿 공급 이중 경로 확정 — 개발 런처(비밀번호 프롬프트) + 배포 시점 주입

### Grounding
- Git Context: `hash:4958e4f`
- Evidence: `scripts/dev/run-local.ps1`, `docker-compose.yml`(env_file), `bw status`(이 머신 로그인 상태 확인)
- Confidence: 4/5

### Design Decision
시크릿(Vaultwarden, 피닉스 금고)을 머신과 무인 컨테이너가 **각각 다른 경로**로 받는다:
1. **개발 머신**: `scripts/dev/run-local.ps1` — 사용자가 터미널에서 실행, 마스터 비밀번호
   프롬프트(마스킹) → `bw unlock --passwordenv`(명령줄 노출 방지) → 금고에서 KIS
   자격증명을 환경변수로 주입(이 프로세스 트리만) → `cargo run --release`.
   unlock 세션은 `~/.bw_session`에 갱신 → 에이전트 세션과 공유.
2. **배포(피닉스 컨테이너)**: 세션 불가(24/7 무인·만료됨) → **배포 시점 주입** —
   개발 머신에서 bw로 조회한 값을 서버 `.env`(600)로 전송, compose `env_file`이 주입.
   이미지·공개 저장소에는 미포함(compose 주석으로 이미 설계되어 있었음).

### Alternatives Considered
- 서버에서 bw 상주 실행 — 세션 만료 관리를 무인 서버에 떠안김 — 기각
- 이미지 빌드 시 시크릿 인자 전달 — 공개 저장소 이미지 파이프라인에 시크릿 근접 — 기각
- 선택: 위 이중 경로 — 마스터 비밀번호는 언제나 사람 입력에만 존재

### Analysis
- Context: GLM 자동 호출·KIS 모의 실증 카드가 시크릿을 요구, 공개 저장소 운영.
- **Trade-offs**: 런처 실행마다 unlock 프롬프트(잦으면 번거로움) vs 시크릿 디스크 무저장 —
  세션 파일 공유로 완화(런처 1회 → 에이전트 재사용).
- Reversibility: High(스크립트·env_file 교체만).
- 함께 발견·정리: 루트 `Dockerfile`이 Python 시절 것으로 남아 있었음(compose는
  rust/Dockerfile 사용, root 것은 src/ 없어 빌드 불가) — 삭제. 이 머신 bw는 이미
  금고 로그인 완료 상태(2026-08-21)였음 — 남은 조작은 unlock뿐.
- Verification: 비대화형 실행 가드 동작 확인(잠긴 금고+리다이렉트 stdin → 즉시 실패),
  `python -m pytest scripts/check_docs.py` 통과.
