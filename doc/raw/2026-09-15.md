## Case 1: Rust 도메인 모델 — 오류를 타입으로, 복구를 구조체로

### Grounding
- Git Context: `hash:4a4efb4`
- Evidence: rust/lossfunction/src/domain/{mod,order,portfolio}.rs
- Confidence: 5/5

### Design Decision
- Python(pydantic ValidationError + 도메인 예외)의 이분법을 Rust에서는
  **Result<_, DomainError> 열거형 하나로** — 생성 규칙과 행위 규칙의 구분은
  에러 변형명(NonPositiveQuantity, WrongStatus...)이 대신한다.
- `Order::restored(RestoredOrder)` — 복구 경로 파라미터를 구조체로 묶어
  clippy too_many_arguments 회피 + 호출 지점 가독성 확보.
- `with_status`는 실행 계층의 유일한 상태 변경 지점(불변 업데이트 스타일
  유지 — self 복제 후 검증).
- Portfolio는 BTreeMap<Symbol, PositionState> — Symbol에 Ord 파생으로
  결정적 순회 보장.
- 분수 평단가(110/7)도 Decimal 정확 산술임을 테스트로 단정.

### Error (Rust 학습 포인트)
```
error[E0408]: variable `price` is not bound in all patterns
```
or-패턴의 한 갈래에만 바인딩 불가 — guard가 필요한 갈래는 별도 arm으로.
```
error[E0599]: the method `as_display` ... trait bounds were not satisfied
```
thiserror `#[error("{status}")]`는 Display 요구 — OrderStatus에 수동 구현.

### Verification
- `cargo test` → 15 passed (형상 5·정정/취소 4·집계 7 포함, Python 도메인
  테스트 시맨틱 이식)
- `cargo clippy` 경고 0, `cargo fmt --check` 통과

### Related Knowledge
- Concepts: [[rust-migration]]
- Patterns: [[errors-as-enum]], [[params-struct-for-arity]]
- **Anti-Patterns**: or-패턴 갈래별 바인딩 혼용; thiserror 포맷에 Display
  없는 타입 사용

## Case 2: Rust 저장 계층 — sqlx 0.8 API 실무 노트

### Grounding
- Git Context: 이 커밋
- Evidence: rust/lossfunction/src/storage/{mod,money,migrations}.rs
- Confidence: 5/5

### Design Decision
- Python(aiosqlite+수동 BEGIN IMMEDIATE+Lock)을 sqlx 풀 트랜잭션이 대체 —
  직렬화는 SQLite 자체가 보장. 저장 규약(1e-4원 정수, 앱 공급 ISO 시각,
  쓰기 트랜잭션 내 audit)은 그대로.
- rust_decimal의 scaleb는 기본 비활성(maths feature) — **상수 10000 곱셈 +
  mantissa()** 로 스케일 변환, 의존 추가 불필요.

### Error (sqlx 0.8 학습 포인트)
```
error[E0277]: the trait bound `SqliteConnection: sqlx::Database` is not satisfied
```
`Transaction<'_, DB>`은 커넥션이 아니라 **데이터베이스 타입**(`sqlx::Sqlite`)
을 받는다. 원시 커넥션의 begin은 소유 이동 — 풀에서 시작하는 것이 정석.
- 모듈 상단 import는 비테스트 코드만 보고 판정 — 테스트 전용 import는
  tests 모듈 안으로 (unused warning 회피).

### Verification
- `cargo test` → 21 passed (마이그레이션 멱등, 주문 수명주기+audit 순서
  단정, 화폐 왕복/반올림, 견적 스케일, record_event)
- clippy/fmt 클린

### Related Knowledge
- Concepts: [[rust-migration]], [[sqlite-storage]]
- Patterns: [[pool-transactions]], [[const-scaling-no-feature]]
- **Anti-Patterns**: Transaction<커넥션타입> 실수; rust_decimal maths feature
  없이 scaleb 호출

## Case 3: Rust 리스크 계층 — 안티패턴이 실제로 재발했다

### Grounding
- Git Context: 이 커밋
- Evidence: rust/lossfunction/src/risk.rs
- Confidence: 5/5

### Error (위키 안티패턴 재현)
```
assertion `left == right' failed
  left: PositionQuantityExceeded
 right: GrossExposureExceeded
```
Python 세션에서 직접 기록한 안티패턴("단일 종목으로 총 노출 한도 테스트면
종목 상한이 선발화")을 Rust 이식에서 또 범했다 — 검사 순서가 의미를 가진
시스템의 테스트는 "무엇이 먼저 걸리는지"까지 설계해야 한다는 교훈 재확인.
수정: 미보유 제3 종목 주문으로 gross 발화.

### Design Decision
- kill switch는 Mutex<(bool, Option<String>)> — &self API로 토글 가능하게
  (서버 핸들러가 공유 참조로 제어). 검사 순서 Python과 동일.
- chrono의 시간 차는 TimeDelta(Duration 아님) — from_std로 변환.

### Verification
- `cargo test` → 28 passed (한도 4종·신선도·누락·kill 우선+해제·멀티심볼 gross)
- clippy/fmt 클린

### Related Knowledge
- Concepts: [[risk-layer]], [[rust-migration]]
- **Anti-Patterns**: 위키에 기록된 안티패턴을 이식 시 재범 — 이식 전 관련
  안티패턴 페이지를 먼저 읽을 것

## Case 5: Rust 런타임 — HashMap 순서가 결정론을 깠다

### Grounding
- Git Context: 이 커밋들(오케스트레이터+데모 루프)
- Evidence: rust/lossfunction/src/runtime/{mod,demo}.rs
- Confidence: 5/5

### Error
```
assertion `left == right' failed
  left: [("069500", 5, "99315")]
 right: [("005930", 5, "79452")]
```
demo_is_deterministic가 3회 중 2회 실패. 원인: tick()이 HashMap 키 순서로
RNG를 소비하는데 **HashMap 순회 순서는 인스턴스마다 무작위** — 같은 시드여도
두 루프의 가격 갱신 순서가 갈라짐. 심볼 정렬 순회로 고정, 5연속 그린.

### Design Decision
- TradingRuntime은 상태머신/게이트웨이/조정기를 소유, RiskManager만
  Arc 공유(서버 제어용). sync와 reconcile 분리 유지.
- 데모 RNG는 xorshift64* 자작 — rand 의존 없이 결정론 보장.
- 재현성 테스트는 1회가 아니라 **연속 5회** 돌려야 믿을 수 있다(이번 교훈).

### Related Knowledge
- Concepts: [[rust-migration]]
- Patterns: [[sorted-iteration-determinism]]
- **Anti-Patterns**: RNG/집계를 HashMap 순회 순서에 의존; 재현성 테스트 1회
  통과로 안심
