## Case 1: 모의투자 자격증명 네이밍 — 금고 항목 "KIS 모의투자", env 변수는 기존 재사용

### Grounding
- Git Context: `hash:352cef7`
- Evidence: `rust/lossfunction/src/config.rs`(KIS_ENVIRONMENT/KIS_APP_KEY/KIS_ACCOUNT_NUMBER),
  `scripts/dev/run-local.ps1`·`backfill-daily.ps1`(-KisItem "KIS 실전투자", username=AppKey·
  password=AppSecret·notes=계좌번호), vaultwarden-secrets 스킬 항목 컨벤션(`<서비스> <용도>`)
- Confidence: 5/5

### Design Decision
오너가 한국에서 KIS 모의투자 서비스 재신청 중(10-02 불가 판정 후 상황 변화). 승인되어
모의 AppKey/SecretSecret/가상계좌가 발급되면:

1. **금고 항목명: `KIS 모의투자`** — 실전 항목 `KIS 실전투자`와 완전 대칭인 로그인 항목.
   구조도 동일: username=모의 AppKey, password=모의 AppSecret, notes=가상 계좌번호.
2. **코드 env 변수: 새로 만들지 않는다.** config.rs는 이미 `KIS_ENVIRONMENT=mock|real`로
   도메인을 선택하고 자격증명은 `KIS_APP_KEY`/`KIS_APP_SECRET`/`KIS_ACCOUNT_NUMBER`
   하나만 읽는다. 모의 전환 = `KIS_ENVIRONMENT=mock` + 같은 변수에 모의 값 주입.
3. **런처 전환점: `-KisItem` 파라미터 하나.** `run-local.ps1 -KisItem "KIS 모의투자"`
   형태로 금고 조회 대상만 갈아끼운다. 런처 코드 수정 불필요(이미 파라미터화됨).

### Alternatives Considered
- Option A: env 변수를 `KIS_MOCK_APP_KEY` 식으로 분리 — 기각: config.rs가 환경 단위
  스위치(KIS_ENVIRONMENT) 설계라 분리가 이중 표현. 실전/모의 동시 기동(실시세=실전,
  주문=모의) 시나리오가 오면 그때 재의.
- Option B: 금고 항목을 "KIS 모의투자 AppKey"처럼 키 단위로 쪼개기 — 기각: 실전 항목이
  로그인 항목 하나(username/password/notes) 구조인데 어긋나면 런처 3곳을 고쳐야 함.

### Decision Code
```powershell
# 승인 후 오너가 금고에 생성(에이전트는 항목 생성 불가 — 스킬 규칙):
#   항목명: KIS 모의투자 (로그인 항목)
#   username = 모의 AppKey, password = 모의 AppSecret, notes = 가상 계좌번호
# 가동:
./scripts/dev/run-local.ps1 -KisItem "KIS 모의투자"   # + KIS_ENVIRONMENT=mock 세팅
```

### Analysis
- Context: 모의 도메인 복귀(10-02 Case 1, Reversibility High)가 현실화되는 첫 준비 단계.
  네이밍을 미리 고정하면 승인 직후 무인 카드가 배선 차례를 놓치지 않는다.
- **Trade-offs**: 단일 자격증명 슬롯(환경 스위치) vs 동시 기동 유연성 — 현재 요구는 전자.
- Reversibility: High (금고 항목 추가만으로 복귀, 실전 경로 무영향)

  조용히 가상 계좌를 보게 되어 실증 오염
