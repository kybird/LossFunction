### Error (서버 로그, 원문)
```text

```
부수 증상: DB 페이지(overview/positions/data) 30초+ 행업 — 10시간 만에 2.25GB로 자란
DB를 집계 쿼리가 풀스캔. /healthz·/strategies(DB 미경유)는 정상 → 앱이 아니라 DB 경로 문제.

### Fix Code
```rust
// runtime/mod.rs — TradingRuntime::new
static BOOT_STAMP: std::sync::OnceLock<i64> = std::sync::OnceLock::new();
...
order_prefix: format!("{}-b{}", order_prefix.into(),
    BOOT_STAMP.get_or_init(|| chrono::Utc::now().timestamp()),
```

### Analysis
- Root cause: `order_seq`가 메모리 카운터(0 시작)라 **프로세스 재시작마다 리셋** — 지속 DB에
  남은 옛 "ord-NNNN"과 새 프로세스가 같은 ID를 발행해 UNIQUE 위반. 데모뿐 아니라
  **재시작하는 모든 지속 DB 운영(페이버·실전 포함)에 적용되는 결함**이었다. 부팅 스탬프로
  접두를 스코핑: 재시작해도 ID 공간이 분리되고, 같은 부팅 내 멱등성(재시도=같은 ID)은 그대로.
- 검증: 169 테스트 통과 → 재배포 → 볼륨 리셋 후 데모 로그 깨끗(오류 0건), 페이지
  /·/positions·/data 전부 200(≤0.08s), DB 576K 출발.
- 남은 관찰: DB 증가율 — 수정 전 2.25GB/10h는 오류 재시도 폭주가 포함된 참고치. 정상
  루프의 증가율을 며칠 관찰해 디스크(24G 여유) 대비 수명 판정(무소속 카드로 추적).
- 접근 패턴 확정: UI 접근은 SSH 터널(`ssh -N -L 18080:127.0.0.1:18080 vault`, Windows
  OpenSSH — 에이전트 키) — 루프백 바인딩 설계 유지, 매매 컨트롤면 비공개.

## Case 2: 체결·주문 내역에 전략 사유 표시 — 결정 근거의 스냅샷 파이프라인

### Grounding
- Git Context: `hash:4c8c59c`(ID 충돌 수정 직후) → 워킹트리
- Evidence: 서버 UI 원문(아래), migration v5, storage/runtime/web 변경
- Confidence: 5/5

### Design Decision
오너 요청: "최근 체결에 사유를 넣어달라 — 어떤 근거로 사고 팔았는지." 근거(rationale)는
`StrategyDecision`에 이미 존재하지만 주문·체결과 연결이 없어 UI에 못 보였다. 선택:
**주문 생성 시점에 orders.rationale로 스냅샷** (migration v5)하고 fills 조회를 orders에
LEFT JOIN. 대안이었던 "체결 시점 조인 당시 상태"는 전략 교체 시 근거가 변조될 수 있어
기각 — 주문이 나간 순간의 이유가 역사적 사실로 남는 스냅샷이 감사 원칙에 맞다.

### Results (서버 UI 원문, 배포 직후)
```text
최근 체결 ... 사유
11-21 01:40:10 NAVER 035420 매수 5 40706 203,530 buy symbols at/below entry with no existing position
11-21 01:07:08 KODEX 200 069500 매수 5 99371 496,855 (빈 — 기능 도입 전 주문)
```
- 구현: migration v5(orders.rationale TEXT DEFAULT '')·create_order(+rationale)·
  run_decision_cycle이 Vec<(Order, rationale)> 반환·demo/sim/realtime 3경로 갱신·
  fills/orders 쿼리 조인·개요·포지션 페이지 사유 열(esc() 이스케이프).
- 검증: cargo test 169 통과(마이그레이션 개수 어설션 4→5 갱신 포함), 서버 재배포
  3초 healthy, 신규 체결에 사유 렌더 확인.

### Analysis
- Why non-obvious: 근거는 이미 시스템 안에 있었다 — 보이지 않았던 이유는 '주문과 근거의
  조인'이 없어서. 기능 추가가 아니라 연결이 문제였다.
- Trade-offs: 스냅샷 방식은 전략이 바뀌어도 옛 주문의 사유가 불변(장점)인 대신 스키마
  확장(migration)이 필요했다. 기존 행은 빈 사유(기본값)로 호환.
- 패치 교훈(재발 방지): 이 세션은 heredoc-python 패치의 백슬래시 이중 이스케이프로
  어설션이 조용히 죽은 뒤 뒤따르는 배포가 미반영 코드로 진행된 사례가 이미 있어
  (2026-11-20 Case 15) — 이번엔 Edit 도구+파일 재독으로 원천 차단.

### Related Knowledge
- Concepts: [[docs-as-tests]], [[trading-core-determinism]]
- **Anti-Patterns**: 결정 근거를 주문과 다른 수명주기(메모리·후회 복원)에 두기 —
  근거는 주문 행에 스냅샷으로 남겨야 감사가 성립한다.

## Case 7: 틱 기록 가격 변화 게이트 — 디스크 예산과 무손실 원칙

### Grounding
- Git Context: `hash:b62cad5`(정규장 필터 직후) → 수정 커밋 `hash:965cdc4`
- Evidence: realtime.rs(note_price_change), 서버 df(45G 중 15G 여유, 빌드 캐시 ~9G), /data 7.5M
- Confidence: 4/5

### Design Decision
오너 질문 "모든 종목 트래킹? 분봉? 디스크 고려하자". 현황: 15종목 체결통보 구독, 쌓이는 건
분봉이 아닌 틱 스냅샷(500ms 최신가) — 같은 가격 반복·제자리 재샘플이 디스크를 태웠다.
선택: **가격 변화 시에만 기록** — 분봉 OHLC는 무손실(시가·고가·저가·종가는 정의상 가격
변화, 볼륨은 애초에 미기록), 낭비는 원천 제거. 대안 '5초 간격 강제'는 고가/저가 스파이크를
놓칠 수 있어 기각.

### Analysis
- 디스크 수학: 수정 전 ~40-70MB/거래일 상한 → 수정 후 실제 가격 변화에 비례. 분봉 집계는
  15종목×390분/일≈5,850행/일 — 사실상 무료. 압박의 실체는 빌드 캐시(~9G) — 정리 여지 기록.
- 교훈(구현): `pending` 키 대여 중 `&mut self` 호출 충돌 — 연관 함수로 맵만 전달하는 필드
  분리 대여로 해결. 첫 배포가 이 컴파일 오류로 실패했으나 구컨테이너가 계속 서빙해 다운
  타임 0(컨테이너 스왑 배포의 이점 실증).
- 검증: 173 테스트 통과, 재배포 — 시딩 16,451봉·구독·MockBroker 헬스 유지. 월요일 실측
  기록량을 DB 관찰 카드에서 확인.
