## Case 1: 주말 무틱 오판 — 달력을 먼저 봤어야 했다 (에이전트 교훈)

### Grounding
- Git Context: `hash:9c9f490`(앵커 수정) — 오판 시점은 워킹트리
- Evidence (피닉스 실측, 토요일 11-28):
  - "quotes today(11-28) = 0" + 어제(11-27 금) 83,001틱 — 요일 확인 없이 "금요일 장중 사고"로 진단
  - 진단 로그 실측: `ws watchdog diag: remaining=600s session=false tick_age=None started_age_ms=64600`
    — **session=false가 정답**(2026-11-28 = Saturday, 2026-01-01(목)+331일 → 주말). 감시는 정상 휴면
  - 11-24 any-frame 감시의 정상 발동 실측: 어제 밤 재접속 → 03:01:59Z(12:01 KST) "ws connected — 15
    subscription(s) replayed", 어제(금) 세션은 83k틱 정상 유입

### Discovery
"장중 틱 0"을 보고 달력 확인 없이 사고로 판정 → 데이터 감시·앵커 수정 2번의 배포와 진단
로깅까지 수행. 전말은 **주말**이었다. 그 과정에서 만든 것들은 버리지 않는다:
- **앵커 수정(9c9f490)은 실제 결함 수정**: per-call timeout 창이 keepalive마다 리셋되는 결함은
  테스트(keepalive_only_session_triggers_first_tick_stall_reconnect)로 증명됨 — 장중
  "구독됐는데 첫 틱 없음" 케이스를 보호한다. 존치.
- 11-24 any-frame 감시는 설계대로 작동(96시간 6회 야간 재접속 실측).
- 감시 설정 기동 로그("watchdogs: silence=600s tick-stall=180s")는 배포 식별자로 존치.

### Analysis
- Why non-obvious: "틱 0"은 (1) 사고 (2) 휴장 (3) 데이터 감시 발동 대기 — 셋 중 하나다.
  **개장일 판정이 진단의 0단계**다. is_regular_session_utc가 있는데도 사람(에이전트)이
  요일을 확인하지 않았다 — 도구가 있어도 절차를 안 밟으면 소용없다.
- 토큰 1일 1회 원칙과 같은 계열: 무의미한 진단·재배포도 approval key·토큰을 소모한다.
- 커밋 메시지 2건(4895834·9c9f490)에 "Friday mid-session"이라는 거짓 전제가 들어갔다 —
  공개 저장소다. 되돌릴 수 없는 기록이니 이 raw 로그가 정정의 SSOT.

## Case 2: Hermes 내부 연동 — 배경 조사와 설계 (구현 전 조사 기록)

### Grounding
- Evidence: server.rs 라우트 실측(단일 리스너: HTML 페이지 + JSON /healthz·/strategies +
  POST 제어 6종), docker-compose.yml 포트 바인딩 `127.0.0.1:18080->8080`,
  server.rs:3 주석 "Controls share the page listener — loopback-only by deployment
  default" — **코드 레벨 인증 없음, 방어선은 배포 바인딩**
- Hermes(hermes-agent 게이트웨이)는 같은 피닉스에서 루프백 8642/9119로 상주.

### Discovery
오너 요구: 헤르메스가 LossFunction을 모니터링·컨트롤하게 하고 싶다 — 이 앱은 터널 외
외부 접근 불가 구조라 내부 에이전트 감시가 가치 있다. 조사 결과:
- **전용 분석 API 포트는 없다** — 단일 포트(컨테이너 8080→호스트 127.0.0.1:18080)에서
  HTML 상태 페이지 + 일부 JSON(/healthz, /strategies) + POST 제어만 존재.
- Hermes 컨테이너→호스트 루프백(127.0.0.1:18080)은 도달 불가(바인딩이 루프백 한정).
  **해법: docker user-defined network** — 두 컨테이너를 같은 네트워크에 편입하면
  `http://lossfunction:8080`으로 컨테이너 간 직접 도달(호스트 노출 추가 0).
- 제어 엔드포인트(kill-switch·backfill 등)는 in-app 인증이 없어 네트워크 편입 시
  해당 네트워크의 모든 컨테이너가 호출 가능 — 신뢰 경계 명시 필요.
- 기계판독성 보강: 분석 결과(전략 제안·백테스트·스크리너)는 HTML에만 있어
  /api/status 류 JSON 엔드포인트 추가가 자연스럽다.

### Analysis
- Why non-obvious: "API 포트가 있나"의 답이 이분법이 아니다 — 제어는 있고 읽기는
  HTML 위주인 단일 포트. 모니터링 자동화에는 JSON 읽기 엔드포인트가 병목.
- 대안 기각: 호스트 네트워크 모드(Hermes 보안 포스트처럼 변경)·호스트 루프백 추가
  바인딩(불필요한 노출). user network가 최소 변경.
- 잔여 위험: 제어 무인증 — 단일 테넌트 박스(자기 컨테이너들만)에서 수용 가능하나
  토큰 추가는 카드 AC로 남긴다.
