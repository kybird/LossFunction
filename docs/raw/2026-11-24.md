# 2026-11-24

## Case 1: 장중 무틱 사고 — WS 무음 스톨이 감지 불가였던 구조 결함, 무음 감시 재접속으로 해결

### Grounding
- Git Context: `hash:7288cc6`(감시 로직) → `hash:92f5228`(카드 done) — 사고 발견은 커밋 전 워킹트리
- Evidence (피닉스 실측, 11-24 10:44 KST):
  - healthz 정상인데 데이터 없음: `{"broker":"MockBroker",...,"status":"ok","uptime_seconds":5323}` + quotes 테이블 `MAX(quoted_at) = 2026-11-23T06:12:16Z` (어제 15:12 KST, 오늘 0행)
  - 무음 스톨의 로그 흔적 = **없음** — "ws disconnected — reconnecting" 3건은 모두 재시작 전 옛 세션 것
  - 재시작 직후: "ws connected to ws://ops.koreainvestment.com:21000 — 15 subscription(s) replayed" + first live tick 15종목

### Discovery
어제(11-23) 14:00 KST에 맺은 KIS WS가 밤새 **조용히 죽어** 있었다. TCP close도 없고
PINGPONG도 안 오니 `recv()`가 영원히 대기 — 소켓 오류가 없으니 재접속 루프가
발동할 이유가 없었다. 개장(09:00) 후 2시간 틱 0. 수동 `docker restart`로 회복을
확인(15종목·401틱)했고, 구조 수정:
- `recv`에 무음 감시 부착: 어떤 프레임도 N초(REALTIME_WS_STALE_SECS, 기본 600)간
  없으면 재접속 — 신규 approval key 발급 + 구독 재생이 재접속에 내재
- WsLiveness 원자 카운터(연결·마지막 프레임·마지막 틱) → 상태 페이지 개요 카드가
  "실시간 WS 연결됨 · 틱 n초 전 · 프레임 n초 전"으로 분리 표기
- 회귀 테스트: 무음 연결(영원히 pending하는 recv) → 감시 재접속·구독 재생·liveness 갱신

### Analysis
- Why non-obvious: "healthy"는 프로세스가 살아있다는 뜻이지 데이터가 흐른다는 뜻이
  아니다. healthz 계약(프로세스·kill switch 상태만)은 옳았고, 빠진 건 **데이터 유입
  신호와 연결 신호의 분리**였다.
- 승인키는 /oauth2/Approval(REST 토큰과 무관)에서 재접속마다 새로 발급 — 일일
  재인증은 재접속에 내재. REST 토큰 캐시는 별도 카드(KIS-토큰-디스크-캐시)로 존치.
- 무음 감시는 비거래 시간대에도 발동한다(설계 선택): 밤새 keepalive 없으면
  10분마다 재접속하지만 paper 모드에서 무해하고 개장 시 항상 신선한 키를 보장한다.

### Related Knowledge
- Concepts: [[kis-websocket]], [[fail-loud]], [[deployment-operations]]
- **Anti-Patterns**: 소켓 오류만 재접속 트리거로 쓰기 — 무음 절단(연결 유지·데이터 정지)은
  오류가 아니라 침묵으로 온다. 침묵 감시가 필요하다.

## Case 2: 배포 경로 전환 — 원격 1G 박스 빌드(30분+) → WSL Docker 빌드 + docker save|load(수 분)

### Grounding
- Git Context: `hash:7288cc6`(이미지에 포함된 커밋) — 배포 실행은 워킹트리
- Evidence: 원격 `docker compose build` 30분+ 경과 후에도 이미지 미갱신·빌드 프로세스 부재
  (스크립트 대기 중단 대비), WSL 빌드 성공 로그 `#17 naming to docker.io/library/lossfunction-runtime:latest`, 
  전송 후 서버 `Loaded image: lossfunction-runtime:latest` + `f86c50c42099 About a minute ago`

### Discovery
deploy.ps1(원격 빌드) 배포 중 원격 빌드가 비정상적으로 오래 걸려(1코어 1G 박스에서
cargo release 재컴파일) 오너가 배포 지연을 지적 → 오너 힌트(WSL 호환)로 WSL2
Ubuntu-24.04의 Docker에서 같은 Dockerfile로 이미지를 빌드(x86_64 리눅스, 피닉스와
동일 플랫폼) → `wsl docker save lossfunction-runtime | ssh vault 'docker load'`
로 밀어 올리고 `docker compose up -d`로 재기동. 전송 ~1분, 전체 수분.
오너의 배포 재개 조건 배경: 배포 카드가 11-23 이미 완료돼 있었다(다른 세션).

### Analysis
- Why non-obvious: deploy.ps1의 tar→scp→원격 빌드 흐름은 "빌드를 서버가 한다"가
  전제인데, 1G 박스에서의 cargo release가 병목. WSL Docker가 있는 머신에서는
  이미지 자체를 산물로 전송하는 게 정답.
- 주의: docker compose up -d는 서버의 .env(자격증명)를 유지 — tar가 docker-compose.yml만
  덮으므로 안전. WSL Docker 데몬은 Docker Desktop 통합(`/usr/bin/docker`, 28.1.1 x86_64).
- 남은 것: deploy.ps1에 WSL 빌드 경로 공식화(-Local 플래그 류) — 무소속 카드로 등록.

### Related Knowledge
- Concepts: [[deployment-operations]], [[windows-polluted-service-env]]
- **Anti-Patterns**: 1G 박스에서 컴파일 — 개발 머신에 리눅스 도커가 있으면 빌드 산물을
  옮기는 게 시간 등가교환에서 항상 이긴다.
